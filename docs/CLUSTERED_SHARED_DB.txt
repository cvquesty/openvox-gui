OpenVox GUI — clustered database and Spock runbook
==================================================
Audience: standing up a new two-console estate (or adding a second
          console to an existing mesh)
Train:    openvox-gui 3.12.0 on `main`
Related:  INSTALL.md (AIO first; clustered is opt-in)
          docs/ESTATE_HEALTH.md (post-install checks)
          docs/FEATURES.md (live fleet / HAProxy vs DNS RR)
          TROUBLESHOOTING.md (GUI count ≠ PDB)
          backend/alembic/README.md (schema versions)

Read section 0 before you type any SQL. The week of field work this
runbook replaces was almost entirely "we treated two databases as one
Spock mesh."


------------------------------------------------------------------------
0. TWO DATABASES, TWO SPOCK MESHES
------------------------------------------------------------------------

There are two Postgres databases on the ovdb hosts. They share a
Postgres *instance*. They do **not** share replication.

  Database        Who writes it              Spock mesh
  --------------  -------------------------  ----------------------------
  puppetdb        Compilers (catalogs,       Existing OpenVoxDB mesh
                  facts, reports)            (n1 → n2/n3/n4)
  openvox_gui     The GUI (ENC, users,       Separate mesh, or WAN to
                  sessions, cluster_secrets) n1 only (day-1)

Rules that prevent the failures we already hit:

  1. Never create GUI tables inside database "puppetdb".
  2. Spock on "puppetdb" does not copy "openvox_gui". CREATE DATABASE
     is local — you must create the empty database on every ovdb peer.
  3. An empty openvox_gui database is only a container. Application
     tables appear after bootstrap (create_all + alembic stamp) or the
     first GUI start against postgresql+asyncpg://…/openvox_gui.
  4. /nodes (what the GUI shows) follows **catalogs**, not SQL INSERT
     into certnames. Do not invent fleet rows in puppetdb.
  5. Both consoles use the identical OPENVOX_GUI_SECRET_KEY and the
     same OPENVOX_GUI_DATABASE_URL. Different keys = LDAP works on one
     site only (Fernet cannot decrypt the bind password).

AIO (one console on the OpenVox Server) may stay on SQLite. Two
consoles that classify nodes require one PostgreSQL database named
openvox_gui. Do not NFS-share a SQLite file.


------------------------------------------------------------------------
1. WHAT "DONE" LOOKS LIKE
------------------------------------------------------------------------

Consoles
  openvox.site-a.example.com
  openvox.site-b.example.com
  Same VERSION, same SECRET_KEY, same DATABASE_URL (host = write-region
  ovdb primary, usually ovdb1.site-a.example.com:5432).
  GUI reads OpenVoxDB at ovdb.example.com (DNS RR). Do not put that
  name in /etc/hosts.

Compilers
  server_urls = https://ovdb1.site-a.example.com:8081,https://ovdb2.site-a.example.com:8081
  command_broadcast = false
  reports = store,puppetdb          under [server], not agent [main]
  ENC: OPENVOX_GUI_API_BASE lists both console :4567 URLs.

OpenVoxDB
  Four ovdb members behind per-site HAProxy :8081 (not :5432).
  Spock copies catalogs / factsets / certnames in set "default",
  edges in "pdb_nopk". repl_user can EXECUTE pg_replication_origin_*.

HAProxy vs DNS RR (both get called "VIP")
  ovcompilers.<site>-it.example.com  — real VM + agent. Show on Nodes.
  ovdb.example.com / ovca.example.com — DNS RR only. Hide on Nodes.

Application schema (database openvox_gui), Alembic head
  004_cluster_secrets

  Revision                 Adds
  -----------------------  ------------------------------------------
  001_baseline             Existing GUI tables (users, enc_*, sessions,
                           execution history, …)
  002_add_api_tokens       api_tokens (ovox / Bolt service tokens)
  003_add_role_to_api_tokens
                           role column on api_tokens
  004_cluster_secrets      cluster_secrets (enc:v1: Fernet values)

  Bootstrap path: SQLAlchemy create_all, then `alembic stamp head`
  (schema already present — do not `upgrade` on an empty DB that
  create_all just filled; that races DuplicateTable).
  Later deploys: `alembic upgrade head` via update_local.sh.

Current console knobs that affect clustered reads (GUI .env)

  OPENVOX_GUI_DATABASE_URL          postgresql+asyncpg://openvox_gui:…@ovdb1…/openvox_gui
  OPENVOX_GUI_SECRET_KEY            identical on every console
  OPENVOX_GUI_PUPPETDB_HOST         ovdb.example.com   (RR; not ovdb1)
  OPENVOX_GUI_PUPPETDB_PEERS        ovdb.site-b.example.com
                                    (other site VIP; Overview merges newest
                                    report so Needs attention matches)
  OPENVOX_GUI_PUPPET_CA_HOST        ovca.example.com
  OPENVOX_GUI_PUPPET_SERVER_HOST    compiler LB / a compiler, not the console
  OPENVOX_GUI_FAILED_ALERT_HOURS    8   (annotate stale Failed; does not rewrite badge)
  OPENVOX_GUI_NODE_FRESH_HOURS      24  (annotate stale report; does not rewrite badge)

Compiler-only (not the GUI .env)

  OPENVOX_GUI_API_BASE              https://openvox.site-a.example.com:4567,https://openvox.site-b.example.com:4567
  OPENVOX_GUI_ENC_TLS_VERIFY        default on; 0 restores CERT_NONE
                                    Console cert must chain to the Puppet
                                    CA and the URL hostname must be a SAN.

2. NEW ESTATE: PROVISION openvox_gui WITH THE SCRIPT
------------------------------------------------------------------------

Do not hand-run CREATE USER / CREATE DATABASE unless the script cannot
reach Postgres. install.sh calls the same script when you set the
install.conf knobs.

install.conf (preferred)

  OPENVOX_GUI_DB_BACKEND="postgresql"
  OPENVOX_GUI_DB_ADMIN_DSN="postgresql://postgres:<superuser-password>@ovdb1.site-a.example.com:5432/postgres"
  OPENVOX_GUI_DB_APP_PASSWORD="<app-password>"
  # Multi-node empty DB on each peer (primary first). CREATE DATABASE
  # does not follow PuppetDB Spock:
  OPENVOX_GUI_DB_HOSTS="ovdb1.site-a.example.com,ovdb2.site-a.example.com,ovdb3.site-b.example.com,ovdb4.site-b.example.com"
  # Optional: GUI-database Spock (site-loss ENC). Separate from puppetdb.
  #OPENVOX_GUI_DB_SPOCK="true"
  #OPENVOX_GUI_DB_REPL_USER="repl_user"
  #OPENVOX_GUI_DB_REPL_PASSWORD="<repl-password>"

Or after install, on a host that can reach Postgres as superuser:

  sudo /opt/openvox-gui/scripts/bootstrap-openvox-gui-db.sh \
    --admin-dsn 'postgresql://postgres:<superuser-password>@ovdb1.site-a.example.com:5432/postgres' \
    --app-password '<app-password>' \
    --hosts 'ovdb1.site-a.example.com,ovdb2.site-a.example.com,ovdb3.site-b.example.com,ovdb4.site-b.example.com' \
    --write-env /opt/openvox-gui/config/.env

  Add --spock --repl-user … --repl-password … only when you want the
  GUI mesh (section 4). Day-1 is fine without it: both consoles talk
  to site-A Postgres over the WAN.

What the script does

  - CREATE ROLE openvox_gui (NOSUPERUSER) and CREATE DATABASE
    openvox_gui OWNER openvox_gui on the primary and every --hosts peer
  - GRANT on schema public; REVOKE CONNECT on puppetdb from the GUI role
  - create_all of the application tables on the primary
  - alembic stamp head
  - optional GUI Spock: extension, gui_n1… nodes, dump/restore public
    to peers, subscriptions with synchronize_structure=false
  - writes OPENVOX_GUI_DATABASE_URL into .env

What you still do by hand

  - pg_hba: allow both consoles (and 127.0.0.1) to openvox_gui
      host  openvox_gui  openvox_gui  192.0.2.79/32     scram-sha-256
      host  openvox_gui  openvox_gui  198.51.100.79/32  scram-sha-256
      host  openvox_gui  openvox_gui  127.0.0.1/32      scram-sha-256
    then SELECT pg_reload_conf();
  - Firewall: consoles → ovdb :5432 only. HAProxy today is :8081, not
    :5432. Point DATABASE_URL at the write-region host, not ovdb.example.com.
  - Confirm the GUI role cannot CONNECT to puppetdb.
  - Copy the same SECRET_KEY onto the second console.

Manual SQL (only if the script cannot run) is in Appendix A.


------------------------------------------------------------------------
3. PUPPETDB SPOCK (the mesh that fills /nodes)
------------------------------------------------------------------------

This section is database **puppetdb**. It is not openvox_gui.

Write path (compilers)
  One primary, one failover. command_broadcast = false.
  Spock copies n1 → n2/n3/n4. Four-way DNS RR is **not** a write fan-out.

Read path (GUI)
  OPENVOX_GUI_PUPPETDB_HOST=ovdb.example.com
  Only after every A record agrees on /pdb/query/v4/nodes count
  (cluster-preflight.sh). Until then, Overview can disagree by which
  site stored the last **report**. Membership should already match.

On **every ovdb member** (not the VIP name), once:

  sudo /opt/openvox-gui/scripts/ensure-puppetdb-spock.sh
  # or: --role repl_user --db puppetdb

That grants EXECUTE on pg_replication_origin_oid / _session_setup /
_session_reset / _advance / _create / _drop to repl_user. Without
those grants on PG17, Spock table-sync crash-loops (exit 1 every 2s).

Required sets

  default    catalogs, factsets, certnames
             reports — add when the table has a PK; otherwise a new
             agent run against the site VIP is enough
  pdb_nopk   edges

Never

  - INSERT into certnames / factsets / catalogs and expect /nodes to
    change. /nodes is "nodes that have a catalog."
  - sub_resync_table on certnames or catalogs (FK parents). The apply
    worker will not recover cleanly.
  - Pin ovdb.example.com in /etc/hosts. Members (ovdb1/ovdb2) may stay
    in hosts; the VIP FQDN must come from DNS.
  - Point OPENVOX_GUI_PUPPETDB_HOST at ovdb1.* except as a temporary
    read while you repair Spock. Put it back on ovdb.example.com.
  - Hide ovcompilers.* — those are HAProxy VMs with agents.

Verify

  sudo /opt/openvox-gui/scripts/cluster-preflight.sh
  # /etc/hosts must not pin the PDB VIP
  # every A record's /nodes count must match

  sudo /opt/openvox-gui/scripts/ensure-puppetdb-spock.sh
  # prints spock.tables for certnames/factsets/catalogs/edges/reports
  # and local_sync_status

  /nodes count equal on every ovdb member and both site VIPs.


------------------------------------------------------------------------
4. GUI SPOCK (optional — site-loss ENC)
------------------------------------------------------------------------

This section is database **openvox_gui**. Skip it for day-1 if both
consoles can reach site-A Postgres. Site A down then loses ENC until
you restore a dump on site B or finish this mesh.

  - shared_preload_libraries already has spock (PuppetDB Phase). Do
    not change GUCs.
  - Node names inside openvox_gui are gui_n1…gui_n4 so they do not
    clash with puppetdb node names in the other database.
  - All GUI tables have primary keys. Use set "default" only. Do not
    invent a pdb_nopk set here.
  - Add tables to the set **after** create_all / first GUI start.
    bootstrap --spock does this on the primary, then dump/restores
    public to peers and creates subscriptions with
    synchronize_structure=false (schema already copied).
  - Single writer. Never two Postgres write regions for openvox_gui.
  - When you flip the PDB write region to site B, also flip
    OPENVOX_GUI_DATABASE_URL to the site B primary (or a 5432 VIP you
    do not have today).

Verify on a peer:

  SELECT count(*) FROM enc_nodes;
  SELECT count(*) FROM cluster_secrets;
  SELECT * FROM spock.sub_show_status();


------------------------------------------------------------------------
5. CUT THE CONSOLES OVER
------------------------------------------------------------------------

1. Snapshot site A SQLite if you are migrating a live console:

     cp -a /opt/openvox-gui/data/openvox_gui.db \
           /opt/openvox-gui/data/openvox_gui.db.bak.$(date +%Y%m%d%H%M)

2. Site A .env — keep the existing SECRET_KEY; set:

     OPENVOX_GUI_DATABASE_URL=postgresql+asyncpg://openvox_gui:<app-password>@ovdb1.site-a.example.com:5432/openvox_gui

   If bootstrap --write-env already did this, just confirm.

3. systemctl restart openvox-gui. journalctl -u openvox-gui -n 40.
   curl -sk https://127.0.0.1:4567/health

4. If you did **not** use bootstrap (empty DB, no create_all):
   first start creates tables; then

     cd /opt/openvox-gui/backend
     OPENVOX_GUI_DATABASE_URL=… /opt/openvox-gui/venv/bin/alembic upgrade head

   If bootstrap already stamped head, skip this.

5. Copy ENC/users from SQLite if you need them (pgloader, a small
   SQLAlchemy copy, or re-classify / rely on LDAP). Verify:

     psql -h ovdb1.site-a.example.com -U openvox_gui -d openvox_gui \
       -c 'SELECT count(*) FROM enc_nodes;'
     psql … -c 'SELECT username, role FROM users;'

6. Site B .env: **same** DATABASE_URL and **same** SECRET_KEY.
   Restart. Classification and users must match site A.
   If site B still shows the old SQLite ENC, the URL did not take.

7. Settings → Cluster → Clustered on **one** console:
   compilers, ovdb members, CA members/VIPs, both console FQDNs,
   ENC API URLs (both :4567), backend=postgresql, same asyncpg URL.
   Save. Copy /opt/openvox-gui/data/cluster_config.json to the peer
   (chown puppet:puppet) or Save the same FQDNs there. Secrets live
   in cluster_secrets (Postgres); the JSON is still per-host.

8. Cluster secrets panel: gui_db_password (and pdb_app_password as a
   reference). Rotating SECRET_KEY invalidates every enc:v1: value —
   re-enter them after a key change.

9. Compilers — puppetserver EnvironmentFile / sysconfig, not the GUI .env:

     OPENVOX_GUI_API_BASE=https://openvox.site-a.example.com:4567,https://openvox.site-b.example.com:4567

   puppet.conf:
     node_terminus = exec
     external_nodes = /opt/openvox-gui/scripts/enc.py

   enc.py is HTTP. It tries each URL; 404 = empty production class;
   connect failure = next URL; both down = empty (fail open).
   HTTPS verifies the GUI cert against the Puppet CA and checks the
   hostname (3.12.0-rc.44+). The URL must be a SAN on the console
   cert. localhost skips hostname only. OPENVOX_GUI_ENC_TLS_VERIFY=0
   restores the old CERT_NONE behavior.

   Test: /opt/openvox-gui/scripts/enc.py ovcompiler1.site-a.example.com
   Same YAML if you stop one console. Restart puppetserver after
   changing ENC env.


------------------------------------------------------------------------
6. AFTER INSTALL — RUN THESE
------------------------------------------------------------------------

On each console:

  sudo /opt/openvox-gui/scripts/cluster-preflight.sh
  sudo /opt/openvox-gui/scripts/estate-health-check.sh
  sudo /opt/openvox-gui/scripts/seed-bolt-known-hosts.sh

On each ovdb member:

  sudo /opt/openvox-gui/scripts/ensure-puppetdb-spock.sh

install.sh already runs preflight (warnings only) after writing .env
and copies those four scripts into /opt.

Healthy:

  - estate-health-check.sh PASS on both consoles
  - /nodes count equal on every member and both site VIPs
  - Play on a site-B name from the site-A console (and the reverse)
  - LDAP login works on **both** consoles for the same user
  - First LDAP login provisions default_role (viewer), never operator

------------------------------------------------------------------------
8. ROLLBACK
------------------------------------------------------------------------

Remove OPENVOX_GUI_DATABASE_URL (or set sqlite+aiosqlite:////opt/openvox-gui/data/openvox_gui.db)
and restart. You return to the last local SQLite file. Site B will
diverge again. Keep the .db.bak from section 5 until you are happy.

Alembic downgrade is in backend/alembic/README.md. Reverting a beta
leaves extra columns in place (SQLAlchemy ignores unknown columns)
unless you `alembic downgrade 001_baseline` first.

9. CHEAT SHEET
------------------------------------------------------------------------

Provision GUI DB          bootstrap-openvox-gui-db.sh  (or install.conf)
PuppetDB origin grants    ensure-puppetdb-spock.sh     (every ovdb)
VIP /nodes agreement      cluster-preflight.sh         (every console)
Play / Bolt / ENC         estate-health-check.sh
                          seed-bolt-known-hosts.sh
Schema versions           alembic current / history    (head = 004)
Shared secrets            cluster_secrets in openvox_gui
Compiler ENC              OPENVOX_GUI_API_BASE + enc.py (TLS = Puppet CA)

This release does not: auto-copy sqlite→postgres rows, merge concurrent
ENC PUTs, or put :5432 on the OpenVoxDB HAProxy.


------------------------------------------------------------------------
APPENDIX A — manual role + database (script unavailable)
------------------------------------------------------------------------

On EVERY ovdb (CREATE DATABASE does not replicate):

  PSQL=/usr/pgsql-17/bin/psql
  sudo -u postgres "$PSQL" --no-psqlrc <<'SQL'
  CREATE USER openvox_gui WITH PASSWORD 'GUI_DB_PASSWORD' LOGIN NOSUPERUSER NOCREATEDB;
  SQL

On n1 only, then dump/restore or GUI Spock to peers:

  sudo -u postgres "$PSQL" --no-psqlrc <<'SQL'
  CREATE DATABASE openvox_gui OWNER openvox_gui;
  GRANT ALL PRIVILEGES ON DATABASE openvox_gui TO openvox_gui;
  SQL

  sudo -u postgres "$PSQL" --no-psqlrc -d openvox_gui <<'SQL'
  GRANT ALL ON SCHEMA public TO openvox_gui;
  ALTER SCHEMA public OWNER TO openvox_gui;
  SQL

Prefer the script. It also stamps Alembic and will not leave you with
an empty database that looks "ready."
